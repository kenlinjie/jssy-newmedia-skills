# Obsidian 知识库与 Git 插件

三档都执行。目标是本地笔记能保存、修改可追溯、Git 插件能显示历史。GitHub 账号和远程仓库不是本地使用的前提。

## 选对知识库

- 用户已有库时使用其指定目录，不复制、迁移或整理原有内容。
- 没有库时，建议系统“文档”目录下的 `AI知识库`。确认位置后创建，并在 Obsidian 选择“打开本地仓库”或按当前界面创建库。目录已存在时先检查用途，不能覆盖。
- 用 Git 检查目标是否已经是仓库、是否属于上级仓库、是否为 worktree；`.git` 可以是文件，不只可能是目录。库位于其他仓库内部时先说明，选择隔离的新库或沿用用户明确指定的组织方式，不能把整个文档目录初始化为仓库。
- 若明确沿用上级仓库，自动提交前必须在当前插件中核对并启用“仅限知识库／Limit to vault”（当前实现对应 `limitToVault`，字段仍需按实际版本确认），限制自动提交的包含范围到本库。预览待提交文件，验证没有库外路径；仅第一次手动提交限定路径不够。当前版本无法可靠限制范围时，保留手动限定路径提交，不启用自动提交，并提供独立仓库方案。
- 不把 iCloud、OneDrive 等云盘目录设为默认位置。用户主动选择现有云盘库时沿用；多端同步与 Git 冲突另行处理，不擅自迁移。

## 安装和启用插件

1. 核对 [Obsidian 当前公开版](downloads.md) 与系统 Git 均已安装。Obsidian 的应用版本和安装器版本都要检查。
2. 按 [Git 插件官方安装说明](https://publish.obsidian.md/git-doc/Installation)，在“设置 → 社区插件”中搜索 Git，核对插件 ID `obsidian-git` 与 [Vinzent03/obsidian-git](https://github.com/Vinzent03/obsidian-git)，安装并启用。
3. 从插件当前发布 manifest 检查版本、`minAppVersion`。发现应用过旧时先按官方方式更新 Obsidian，不安装不兼容的新插件，也不静默退回旧插件。
4. 社区商店无法访问时，可从插件官方最新正式发布下载其实际提供的发布资产，按作者说明手动装入该库 `.obsidian/plugins/obsidian-git/`。核对 `manifest.json` 和 `main.js`，样式文件以该发布为准。已有目录先备份并比较，不直接覆盖配置，不使用源码 ZIP 代替编译好的插件。
5. Git 可执行路径优先自动发现。终端可用但 Obsidian 不可用时，检查 GUI 进程的 PATH 或插件的 Git 路径设置，只填真实路径。更改插件设置通过当前界面或已验证的当前配置结构完成，不沿用旧版 JSON 字段。

## 初始化与首次提交

1. 确定 Git 操作范围就是目标知识库，记录既有工作区、暂存区和分支状态。已有仓库不重新初始化，不改默认分支，不重置历史。
2. 新库使用当前 Git 支持的普通初始化方式。复用已有 Git 身份；缺失时询问用户希望用于该库的提交名与邮箱，只写仓库级 `user.name`／`user.email`。无需为了本地提交创建 GitHub 账号，也不写虚构身份。
3. 新库用 [忽略模板](../assets/vault.gitignore) 创建 `.gitignore`。已有 `.gitignore` 只合并缺失的适用规则，保留原内容与换行格式；模板不会隐藏已经跟踪的文件，也不会自动识别私人笔记。
4. 新建一个不重名的 `环境配置验收.md`，写明当天已配置的软件、两句使用说明即可。不要写账号标识、Token、私人业务内容或详细安装日志。文件已存在时换一个唯一名称，不覆盖。
5. 首次只提交本次创建的验收笔记和新建的 `.gitignore`。已有库的其他文件不自动 `git add .`。暂存区已有用户改动时，用明确限定路径的提交隔离本次文件，保留原暂存内容；无法隔离时说明具体冲突，不夹带提交。
6. 读回提交内容与短哈希，确保没有多余文件。让用户在 Git 插件的历史视图看到同一条提交；再打开验收笔记核对内容。

示例中的变量必须先设置为已确认的真实路径，文件名要换成刚创建的实际名称：

```bash
git -C "$vault" status --short
git -C "$vault" log -1 --oneline
git -C "$vault" show --stat --oneline HEAD
```

以上检查不能代替插件内验收。没有可操作界面的工具时，请用户查看插件历史并反馈；未反馈前标记“命令行提交通过，插件内显示待确认”。

## 自动提交与远程备份

先让手动本地提交通过。自动提交、拉取、推送是不同选项；保留已有设置，新库初次默认手动提交，向用户演示如何保存版本。若用户选择自动提交，在当前插件界面设置其希望的间隔与包含范围；没有远程仓库时关闭需要远程的选项，避免持续报错。记录实际读回的自动提交间隔、自动推送是否启用、同步间隔和分支，不能仅记录“已开启备份”。

询问是否需要远程备份；已明确要求的直接配置。无科学上网档可以先只做本地版本管理，远程不可访问不阻塞本地使用。

远程备份启用后：

- 核实用户选择的平台、账号、目标仓库与可见性。个人笔记默认建议私有；只有用户明确要求公开知识库，才可公开。发布这个安装 skill 的授权不等于公开用户知识库。
- 优先复用明确指定的现有仓库；新建仓库、添加 remote 与首次推送依照用户的远程备份指令执行，不重复索要已有授权。已有 remote 不自动替换，含凭据的 URL 不回显。
- 知识库位于上级仓库内部时，即使启用“仅限知识库”，Git 推送仍会上传该分支可达的整个仓库历史，并不只上传这个子目录。先核对用户是否确实要备份整个上级仓库，以及目标 remote 和历史是否适合；若只要知识库，不把上级仓库直接推到新远程，改由用户选择独立仓库组织方式。
- 通过系统凭据管理器或官方登录处理 HTTPS／SSH，不把密码、PAT 或私钥写进笔记、remote URL、插件数据或仓库。无可用凭据时引导官方授权。
- 推送前核对这次实际提交的文件与历史是否适合上传；`.gitignore` 不会从既有历史移除秘密。用户已有未知历史时不能当新空库直接全部推送。
- 推送后比较本地提交与远程分支提交，确认相同；再验证插件的远程操作。已有远程历史先检查差异，不使用强推或丢弃式冲突处理。

用户要求自动备份时，再给刚创建的验收笔记补一行测试内容，观察插件按定时配置自动生成新提交并自动推送，核对本地、远程提交哈希和文件内容。手动点一次提交／推送不算这个验收。可在测试期间暂用当前插件支持的较短合理间隔，完成后恢复并读回用户选定的间隔；不能改动用户其他自动化。当前会话没有观察到自动触发时，记录“手动备份通过，自动备份待验收”，保留已经完成的配置。

## 出错时

- `Author identity unknown`：补当前库身份，不重装 Git。
- `git not found`：检查当前 Obsidian 进程可见的 Git 路径，尤其是 Windows 安装后未重开应用的情况。
- `not a git repository`：核对 Obsidian 打开的库与 Git 初始化目录是否一致，不能向上猜一个目录初始化。
- 认证、无 remote、冲突、push 被拒绝：保留本地提交，分别处理对应原因；不能用关闭校验、硬重置或强推来“通过验收”。
